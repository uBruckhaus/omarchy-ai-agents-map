Update notes for target commit `TARGET_SHA`:

Version 2.3.0 supersedes the pending 1.0.2/2.2.0 request (target `17c937f`). It brings the plugin to Maprisma 2.x (2.0.0 to 2.1.7). The map is unchanged as the plugin's main view. Changes since `17c937f`, grouped by feature:

- **Two findings from the 1.0.2 review, closed**:
  - The Low "automatic AI lookup without opt-in": a lookup now only runs when you click **Look up on the web…** in an agent's menu (`ai_popup.py`, through `plugin_ai.py`). Opening a page, a box or the map starts no lookup. Since 2.1.0, a lookup that fails also clears its "being looked up" mark.
  - Installer supply chain: every local LLM, and every program the plugin downloads and installs itself (Ollama, llama.cpp, KoboldCpp, Jan, mise, …), is one release named in `release_pins.py`: repository, tag, file, size and SHA-256. The download is checked against these before anything is unpacked or run (`install_ctl.Installer.install`, `open_verified`). Nothing comes from a release listing at run time. Agents installed or updated through their own tools are the exception: `mise use -g` / `mise upgrade` and `claude update` use those tools' own release channels, in a terminal you watch and only on Install/Update, as the README says.
- **Projects tab (AI Project Center: `project_center.py`, `project_supervisor.py`, `projects_page.py`, `projects_controller.py`, `project_detail_page.py`, `project_parts.py`)**: a board of your projects and a project page with Goal, Plan, Team, Activity and Setup. A team of your installed agents plans and runs the work in the project's folder, **only when you click** Draft plan / Approve / Run. Before every launch, Settings › Rules (`action_rules`) is checked. Agents run as argv lists, with the prompt on stdin or as one argument, under a supervisor that ends their whole process group (pidfd, start time checked). The store is `~/.config/omarchy/ai-agents-map/ai-project-center/`: 0700, an exclusive `flock`, atomic 0600 writes, and size caps on the store and on prompts.
  - Board: you drag a whole card to change the order, and separators show where it can go. There is no Move menu any more. Ctrl+↑/↓/Home/End still work. AI map: a box moves only inside its own card, onto a separator, and is never dropped into another card (`map_view.order_bar`).
  - In 2.1.0, `harnesses.NEWER_FACTS` includes `project`. The bundled agent add-ons were signed before the `[project]` table existed. With those add-ons switched on (which setup does), the Projects tab treated every agent as "not available". They now get the project commands from the plugin's own adapter for the same agent. An add-on that brings its own `[project]` table keeps it.
- **No scheduled runs in this version.** Versions 2.1.0 to 2.1.7 (2.1.0–2.1.4 pushed to GitHub, none submitted to the marketplace) also ran projects on a schedule with systemd user timers. A static Codex recheck found a Medium in that timer and hand-over plumbing in each of eight rounds, so this version leaves scheduling out entirely instead of patching it further: `project_schedule.py`, `schedule_units.py`, `schedule_handover.py` and their hooks in `project_center.py`, `projects_page.py`, `projects_controller.py`, `project_detail_page.py` and `project_texts.py` are removed (those files are as in 2.0.2, before scheduling). The plugin writes no timer, no `.service` file for projects and no queue. A project runs only when you click. Since 2.1.9 the project's Goal tab says that scheduled runs are in Maprisma, the desktop app the plugin is based on, with a `Gtk.LinkButton` to https://github.com/maprisma/maprisma (`project_detail_page.MAPRISMA_URL`; it only opens the page, nothing is downloaded or installed); README and manual say the same. The README tells anyone who installed 2.1.0–2.1.4 from GitHub how to remove timers left by them. A project store written by those versions still opens (an extra `schedule` field and `schedule_*` events are kept and ignored).
- **Folder picker (`folder_picker.py`)**: the project folder dialog lists mounted disks and pinned folders. GTK bookmarks and favourites are read only from regular files: non-blocking `open`, size cap, no FIFO. At most 64 shortcuts are added, and broken bookmarks are skipped. One dialog is open at a time, and it closes with its window.
- **2.2.0: which agents can join a project team, and a hint what each can do** (`adapters/*.toml`, `adapter_data.py`, `project_center.py`, `ai_core.py`, `project_texts.py`, `project_parts.py`, `project_detail_page.py`):
  - New reviewed `[project]` profiles for GitHub Copilot (planning: `view,glob,grep,rg` only; execution adds `edit,create,apply_patch`; shell, URL and memory tools denied; `-p` refuses whatever no rule approves) and Goose (read-only: `goose run --no-profile --with-builtin analyze`, code structure only; planning and execution keep the user's own goose mode, setup runs without any extension and with `GOOSE_MODE=chat`). Cursor, Oh My Pi, Gemini CLI, DeepSeek Harness, Crush, OpenCode and Grok get none, with a comment in their adapter saying why (each fence could be undone by the user's own config or has no argv-only fence).
  - `[project.env.<plan|run|setup>]`: fixed environment variables for one phase's process. Only audited names with fixed values are accepted (`adapter_data.PROJECT_ENV_NAMES`: `GOOSE_MODE`; Copilot's `COPILOT_ALLOW_ALL`, `COPILOT_ASSISTED_APPROVAL`, `COPILOT_AUTO_UPDATE` and `GITHUB_COPILOT_PROMPT_MODE_EXTENSIONS`/`_REPO_HOOKS`/`_WORKSPACE_MCP`, each only `"false"`, so an exported `true` cannot make Copilot trust the project folder or load its hooks, extensions or workspace MCP). They are checked when the adapter loads, before a team setup changes the project, and at every launch; they are merged over the agent's environment and are part of the plan approval only when declared, so earlier approvals stay valid. No loader, interpreter or shell variable (`LD_*`, `NODE_OPTIONS`, `PYTHONPATH`, `PATH`, …) can be set this way.
  - `CLAUDE_RELAUNCH_*` and `CLAUDE_BG_*` are now agent session variables (`ai_core.is_agent_session_var`) and never reach an agent started by the plugin (`CLAUDE_RELAUNCH_SESSION_ADD_DIRS` would add folders even under `--restricted`).
  - Team tab: a shield button beside a member's agent (hover, click, Enter or Space) shows what that agent can and cannot do in this project, from the same conditions the launch checks (editing only for project-edit or project-commands access on a profile that allows it), plus the profile's own permissions sentence. Text only, no action.
- **2.3.0: Edit + commands access level, plan access gaps, and steps left to you** (`adapters/{claude,codex,agy,copilot,goose,pi}.toml`, `adapter_data.py`, `project_access.py`, `project_center.py`, `project_texts.py`, `project_parts.py`, `project_detail_page.py`, `projects_controller.py`, `projects_page.py`, `docs/manual/manual.html`):
  - Third access level `project-commands` (**Edit + commands**) for Claude Code, Codex and Antigravity (`run_commands` and optional `run_commands_push`, only when the project's **Allow push** switch is turned on; off by default). Claude Code and Antigravity allow only a fixed list of build, test, install (`./install.sh`, `./build.sh`; exact `makepkg` with no `-s`/`-i` flags for Claude, no `makepkg` for Antigravity) and `git commit` commands (exact `make` rules for Claude, no `make` for Antigravity; `git push` only in `run_commands_push`); Antigravity's `plan` and `run` set `"permissions":{"allow":[]}` in `--settings` so global allow rules are not inherited, allowed commands can write `~/.local` and reach the network, and `denied_marker` detects headless auto-denied turns that exit 0. Codex opens only `.git` (`--add-dir .git`, no `~/.local` install grant; opening `.git` also permits writing `.git/config` and `.git/hooks` inside that repository) and enables sandbox network only with **Allow push**. New members default to **Edit project files**, never **Edit + commands**.
  - `[project.capabilities.<level>]` declares probed boolean capabilities (`edit`, `shell`, `network`, `outside_project`, `git_commit`, `git_push`) per level; `adapter_data.py` validates `run_commands`, `run_commands_push`, `capabilities`, `denied_marker` and `[project.env.run_commands|run_commands_push]` using the same audited `PROJECT_ENV_NAMES` allowlist.
  - Before approving a plan or skipping planning, `project_access.py` derives plan needs (from the planner's last fenced `needs` block, else tightened keywords) and computes `access_gaps`. Approval with gaps is refused (`project_access_gaps`) unless `accept_gaps: true` is confirmed (**Leave these to me**), and accepted gaps + `allow_push` are bound into the approval digest (older approvals without `accepted_gaps` stay valid; changing team/plan clears `accepted_gaps`). Strict store load checks reject malformed `accepted_gaps` or `not_done` entries.
  - Runs that finish with accepted gaps, agent-reported `not_done` items, or a `denied_marker` hit keep status `completed` with `partial: true` and show **Done, steps left to you** in amber on board cards and the project page with the list of remaining steps.
  - Note on `needs` block vs. keyword heuristics: the gap check is an advisory pre-flight hint, not a permission boundary (actual runtime permissions come solely from the chosen level's reviewed adapter argv). The planner's explicit fenced `needs` block intentionally overrides keyword heuristics so plans stating "do not push" do not trigger false gaps.
- **Other 2.x features** (Maprisma parity), each started by a click:
  - Ask AI: your request goes to an agent you choose. Its JSON answer is checked against the real setup, and nothing runs from it directly.
  - Reports: an opt-in local activity log (owner-only files, 7 days by default) and Collect history from the agents' own session files. Credentials in topics are redacted (`activity_log`, `agent_activity_report`).
  - What is it doing?
  - Configure for this PC for local LLMs, with a preview, a backup and Undo (`provider_config.py`).
  - 3D map (`map_3d.py`).
  - Settings › Keyboard shortcuts (`settings_pages.SHORTCUTS`; a test checks every listed key against its handler).
  - The free GPU memory of a running local LLM is shown as a memory chip.
